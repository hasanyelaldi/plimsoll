Every ship has a Plimsoll line.

Your service graph should too.

Plimsoll reads the retry, timeout and circuit-breaker settings of your services from real configuration (Java code, Spring YAML, Istio manifests), builds the call graph, and shows where they go past safe limits.

Retries multiply

Each service in this checkout flow retries three times. Looked at one at a time, every setting is reasonable. When the last service is down, the tries multiply along the chain, and one request at the entry becomes a flood at the bottom.

From configuration to evidence

Every number in a report is computed by deterministic code. Every value it used says where it came from: file:line in your configuration, or the library documentation for a default. Reports are meant to be attached to architecture decision records.

What it checks

Seven rules, each finding listing the values it used and their source.

A1 Amplification
Requests one entry request can cause at each service, if every try fails. Attempts multiply along a path and add up across paths; of alternative routes, the largest counts. A cycle is unbounded.
A2a Retry budget
All tries and backoffs of a call against the caller's deadline, and how many tries actually fit.
A2b Abandoned work
The callee may work longer than the caller waits for one try, so it keeps working after the caller gave up.
A3 Non-idempotent retry
A call that is not idempotent, such as a POST, is retried.
A4 Backoff hygiene
Retries with zero backoff, or without jitter.
A5 Layered retries
One call retried by several layers, or one path with retries on several calls.
C1 Not modelled
A retry, timeout or breaker mechanism found in the code that Plimsoll does not model yet, named with file:line.

Read from real configuration

Point it at a directory of services and it collects:

  • Resilience4j retries and time limiters, from application.yml and annotations
  • Spring Cloud Gateway routes, Retry filters and response timeouts
  • HTTP clients: WebClient, RestClient and RestTemplate calls through Spring Cloud LoadBalancer
  • Istio VirtualService and DestinationRule, including Istio's implicit default retries

Whatever it could not read is listed in the report's Coverage section.

Checked against the real libraries

Libraries count differently: Resilience4j's maxAttempts includes the first call, Istio's attempts does not. Plimsoll turns every layer into total attempts, and oracle tests run the real libraries to confirm each behaviour it relies on.

A default without a sourced entry in its knowledge base is reported as UNKNOWN, never guessed.

Install

Plimsoll needs Java 21. Download the jar from the latest release or from Maven Central, and point it at a spec file or a repository:

curl -fLo plimsoll.jar https://repo1.maven.org/maven2/io/github/hasanyelaldi/plimsoll-cli/0.2.0/plimsoll-cli-0.2.0.jar
java -jar plimsoll.jar analyze path/to/spec-or-repo

It exits with 1 when a finding reaches --fail-on (ERROR by default), so it can gate a build. Read the known limitations before you trust a report.

Tried on real systems

Each run is pinned to a commit, and every finding is checked by hand: spring-petclinic-microservices and TrainTicket.
