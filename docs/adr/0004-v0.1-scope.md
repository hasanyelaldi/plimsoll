# 0004 v0.1 scope: Resilience4j, Istio and one HTTP client

- Status: accepted
- Date: 2026-10-14
- Recorded: 2026-11-08 (#62), from the decision list in CLAUDE.md

## Context and problem statement

Retries and timeouts can be set in many places: resilience libraries, service meshes, API gateways, HTTP clients,
message consumers, cloud SDKs. Each one needs a collector, KB entries and an oracle test (ADR 0003). v0.1 has a
fixed date (15 Nov 2026). Which sources does it cover?

## Considered options

1. One source only (Resilience4j).
2. Resilience4j, Istio and one HTTP client.
3. Every common source of the JVM ecosystem.

## Decision outcome

Option 2. Amplification and layered retries only show up when two mechanisms meet on one call. Resilience4j (in
the code) and Istio (in the mesh) are the most common pair on Spring services and they count attempts differently,
which is the first thing the tool must get right. One HTTP client adds the client's own retries and timeouts. Option
1 cannot show layering; option 3 cannot be verified by the release date.

### Consequences

- Out of scope for v0.1: the LLM layer, OpenTelemetry ingestion, SARIF and the GitHub Action, an HTML report,
  Linkerd, queue consumers, cloud SDKs, a dynamic fault-injection harness, performance what-if. New ideas become
  issues labelled `later`.
- Additions made during v0.1, each through an issue in the milestone: Spring Cloud Gateway (#17, #31, #38), because
  it is the entry of the primary testbed (ADR 0005); Spring Cloud LoadBalancer retries and requests found in code as
  the HTTP client (#8, #37); and a detection pass that reports mechanisms no collector models (PLM-C1, #23).
